### 2.6 Q5: 哪些订单和时间窗口可能异常？(8 分钟)

### 3.1 Q6: 为什么同一个分析差这么多？(7 分钟)

  - `apply(axis=1)`
  - `query`
  - NumPy / Pandas 向量化

  - 每行要临时包装成 `Series`

- 性能工程三原则: 
  - 只读真正需要的列
  - 合理收缩 `dtype`
  - Parquet 优于 CSV
- benchmark 纪律: 
  - 所有方案必须做完全相同的工作

# 课后大作业

## 题目: 把出租车分析脚本做成一个可调用的小服务

**目标**: 把 Q1、Q3、Q6、Q7 串起来, 让学生完成一次“数据分析脚本 → 小型服务 → 客户端压测”的闭环.

### 一、作业背景
你现在不是只写 notebook, 而是要把一段可复用的数据分析能力暴露为服务.

服务只需要两个接口: 

1. `POST`: 多次上传文本 CSV 小批次, 服务端把它们持续拼接到同一张累计数据表中
2. `GET`: 在请求中指定固定公式编号, 返回**当前时刻累计数据表**下的计算结果

也就是说, 这道题不再是“一次上传, 一次计算”, 而是一个**增量追加数据**的服务:

- 你可以多次 `POST`
- 每次 `POST` 上传一小批 CSV
- 服务端把这些批次清洗后追加到同一个数据集里
- 服务端并不知道你什么时候会发起 `GET`
- 因此服务端**不能在 POST 阶段把所有公式最终结果提前算死并直接缓存返回**
- 每次 `GET` 都必须基于“当前累计数据”重新计算对应公式

### 二、固定公式说明
本作业只要求支持下面 3 条**提前公布的固定公式**:

1. `F1 = mean(revenue_per_minute)`
2. `F2 = mean(efficiency_score)`
3. `F3 = max(hourly_mean(efficiency_score))`

其中:

- `revenue_per_minute = total_amount / trip_minutes`
- `fare_per_mile = fare_amount / trip_distance`
- `efficiency_score = 0.6 * revenue_per_minute + 0.4 * fare_per_mile`
- `hourly_mean(efficiency_score)` 表示先按 `pickup_hour` 分组, 对每个小时的 `efficiency_score` 求平均值, 再从这些小时均值里取最大值

要求:
1. 学员只需要支持这 3 条固定公式, 不要求支持任意公式字符串.
2. 推荐在接口中传 `formula_id`, 取值为 `F1`、`F2`、`F3`.
3. 服务端内部可以用 `if/elif` 或“字典映射到函数”的方式实现.
4. 若收到未公布的 `formula_id`, 需要返回 `400 Bad Request`.

### 三、输入数据要求
上传的 CSV 至少包含以下列: 

- `tpep_pickup_datetime`
- `tpep_dropoff_datetime`
- `trip_distance`
- `fare_amount`
- `tip_amount`
- `total_amount`
- `payment_type`
- `PULocationID`
- `DOLocationID`

要求: 
1. 文件为 UTF-8 编码文本 CSV.
2. 单次 `POST` 上传的是一个小批次 CSV, 建议每批约 10～30 行.
3. 表头必须存在, 列名必须与上面一致.
4. 数值列若解析失败, 需要返回 400, 而不是静默忽略.
5. 老师验收时会更换 CSV 的具体内容, 不能把结果写死在代码里.
6. 客户端会通过多次 `POST` 持续追加数据, 最终累计原始数据条目总量约 2000 行.

### 四、服务端功能要求

#### 1. `POST /api/datasets`
**功能**: 接收一个 CSV 小批次, 完成解析、清洗、派生字段, 并把它追加到某个累计数据集中.

**请求方式**: 
- `multipart/form-data`

**请求字段**: 
- `file`: 上传的 CSV 文件
- `dataset_id`: 可选字段. 
   - 第一次上传时可不传, 由服务端创建新的 `dataset_id`
   - 后续上传时传回同一个 `dataset_id`, 表示把本批数据追加到同一数据集

**服务端必须完成的动作**: 
1. 读取 CSV 为 DataFrame.
2. 把上车/下车时间转成 `datetime`.
3. 构造 `trip_minutes`.
4. 按 Q1 规则清洗无效行: 
   - `fare_amount > 0`
   - `total_amount > 0`
   - `trip_distance > 0`
   - `trip_minutes > 0`
   - `PULocationID > 0`
   - `DOLocationID > 0`
5. 构造派生指标: 
   - `pickup_hour = tpep_pickup_datetime.dt.hour`
   - `revenue_per_minute = total_amount / trip_minutes`
   - `fare_per_mile = fare_amount / trip_distance`
   - `efficiency_score = 0.6 * revenue_per_minute + 0.4 * fare_per_mile`
6. 如果本次请求没有 `dataset_id`, 则创建新的累计数据集.
7. 如果本次请求带有 `dataset_id`, 则把当前清洗后的批次数据追加到对应累计数据集.
8. 维护该数据集的元信息, 至少包括:
    - `dataset_id`
    - `batch_count`
    - `total_raw_rows`
    - `total_clean_rows`
    - `dataset_version`
9. **只缓存累计后的明细数据和元信息, 不要把 `F1/F2/F3` 的最终数值结果在 POST 阶段全部预计算后直接缓存.**
10. 返回本次追加结果.

**成功返回示例**: 
```json
{
   "dataset_id": "8d8b6c4e-4c3a-4f7a-9b0c-6d9c1e3f2a11",
   "batch_raw_rows": 20,
   "batch_clean_rows": 18,
   "total_raw_rows": 860,
   "total_clean_rows": 804,
   "batch_count": 43,
   "dataset_version": 43,
   "status": "appended"
}
```

#### 2. `GET /api/datasets/{dataset_id}/result?formula_id=F2`
**功能**: 根据 `dataset_id` 和 `formula_id`, 对**当前累计数据集**实时计算结果并返回.

**服务端要求**:
1. 能根据 `dataset_id` 找到当前累计数据集.
2. 若 `dataset_id` 不存在, 返回 404.
3. 从查询参数读取 `formula_id`, 只允许 `F1`、`F2`、`F3`.
4. 每次 `GET` 时, 都要基于该 `dataset_id` 当前保存的累计数据重新计算结果.
5. 若计算失败, 返回 400 或 500, 并给出清晰错误信息.
6. 返回结果时同时带上基础元信息, 便于客户端核对.
7. 推荐额外返回 `compute_ms`, 用于区分“接口总耗时”和“公式本身计算耗时”.

**成功返回示例**:
```json
{
   "dataset_id": "8d8b6c4e-4c3a-4f7a-9b0c-6d9c1e3f2a11",
   "dataset_version": 43,
  "formula_id": "F2",
   "formula_text": "mean(efficiency_score)",
  "result": 1.8427,
   "total_clean_rows": 804,
   "compute_ms": 3.12,
  "status": "ok"
}
```

### 五、固定公式实现要求
推荐把 3 条公式拆成 3 个独立函数, 例如:

1. `calc_f1_mean_revenue_per_minute(df)`
2. `calc_f2_mean_efficiency_score(df)`
3. `calc_f3_peak_hour_efficiency_score(df)`

然后再用一个简单映射分发:

```python
FORMULA_REGISTRY = {
      "F1": calc_f1_mean_revenue_per_minute,
      "F2": calc_f2_mean_efficiency_score,
      "F3": calc_f3_peak_hour_efficiency_score,
}
```

这样做的目的是:

1. 把难点放在 Pandas 清洗与特征构造, 而不是字符串解析.
2. 让服务接口层和计算逻辑层分开.
3. 让后面做 benchmark 时, 更容易解释 POST 慢在哪里、GET 慢在哪里.
4. 明确区分“缓存累计后的明细数据”与“缓存公式最终结果”这两件事.

补充要求:

1. 可以缓存累计后的 `DataFrame` 或等价结构.
2. 不允许在 POST 时把 `F1/F2/F3` 的最终结果全部提前算好, 然后在 GET 时只查字典返回.
3. 如果两次 GET 之间没有新的 POST, 那么同一个 `formula_id` 的结果应保持一致.
4. 如果两次 GET 之间发生了新的 POST 追加, 那么结果发生变化是正常的.

### 六、客户端 Benchmark 要求
写一个独立客户端脚本, 完成以下流程:

1. 准备一份本地测试数据, 总原始行数约 2000 行.
2. 把这份数据切成多个小批次 CSV, 建议每批约 20 行.
3. 第 1 次 `POST /api/datasets` 时不传 `dataset_id`, 由服务端创建数据集.
4. 后续多次 `POST /api/datasets`, 都带上同一个 `dataset_id`, 把批次持续追加进去.
5. 在追加过程中, 至少发起 3 次 GET, 分别测试 `F1`、`F2`、`F3`, 观察随着累计数据增长, 结果如何变化.
6. 当所有批次都上传完成后, 对一个**不再变化的最终累计数据集**分别执行:
   - 10 次 `GET ...?formula_id=F1`
   - 10 次 `GET ...?formula_id=F2`
   - 10 次 `GET ...?formula_id=F3`
7. 分别统计并打印:
   - `post_avg_latency_ms`
   - `get_f1_avg_latency_ms`
   - `get_f2_avg_latency_ms`
   - `get_f3_avg_latency_ms`
   - `get_f1_avg_compute_ms`
   - `get_f2_avg_compute_ms`
   - `get_f3_avg_compute_ms`
8. 校验规则:
   - 如果两次 GET 之间没有新的 POST, 同一公式的结果必须一致
   - 如果中间发生了新的 POST, 同一公式的结果可以变化
9. 用一句话解释:
   - 为什么这道题里 POST 和 GET 的职责不同
   - 为什么要在“数据不再变化”时再比较不同公式的 GET 平均耗时

### 七、推荐实现方式
可以自由选框架, 推荐 FastAPI, 也可以用 Flask. 无须接数据库, 内存缓存即可.

推荐拆成 3 层:

1. 纯函数层
   - `load_and_clean_batch(...)`
   - `build_features(...)`
   - `append_dataset(existing_df, batch_df)`
   - `calc_f1_mean_revenue_per_minute(...)`
   - `calc_f2_mean_efficiency_score(...)`
   - `calc_f3_peak_hour_efficiency_score(...)`
2. 服务层
   - `POST /api/datasets`
   - `GET /api/datasets/{dataset_id}/result`
3. 客户端层
   - `client_benchmark.py`

这样的拆法对应 Q7:

1. 先把分析逻辑写成纯函数
2. 再把纯函数挂到接口上
3. 把“批次清洗 / 累计拼接 / 公式计算”三件事拆开, 以后如果要升级成 Accessor 或 Pipeline, 改动会最小
